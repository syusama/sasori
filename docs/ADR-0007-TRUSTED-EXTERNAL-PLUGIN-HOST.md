# ADR-0007: trusted external tool plugin host and installed identity

Status: proposed on 2026-08-07; not implemented or shipped.

This document is a design and acceptance contract only. Sasori does not
currently ship the installed-byte verifier, immutable plugin lock, external
plugin-host application, or their CLI/HTTP integration described below.
Present-tense requirements in this proposal are requirements for a future
implementation, not statements of current behavior.

## Context

ADR-0001 defines Sasori's manifest, registration, discovery, permission
disclosure, and `trusted_process` loading contracts. The Python loader can
already reject disabled plugins, mismatched distribution metadata, missing
grants, unsupported execution modes, and invalid registrations. Bundled
first-party applications do not use that loader; they compose registrations
directly.

The existing catalog is also intentionally read-only. It can prove that a
retained wheel matches an approved catalog release, but it does not prove that
the files Python will import from `site-packages` came from that wheel. Matching
distribution name, version, and entry-point metadata is not installed-code
identity. A different installation with the same metadata would otherwise be
imported with full host privileges.

This decision closes one deliberately narrow path:

```text
approved local catalog release
    -> retained reviewed wheel
    -> wheel RECORD and payload
    -> installed RECORD and actual files
    -> immutable enabled lock and exact grants
    -> all-plugin import preflight
    -> existing load_enabled_plugins()
    -> existing Harness
    -> Python, CLI, and HTTP adapters
```

It is not a package installer, a remote marketplace, a signature system, or a
sandbox.

## Decision

### 1. The Alpha is an app-layer host, not another runtime

The external plugin host lives outside the core runtime. Supply-chain and
installed-file verification belong under `sasori_market`; application assembly
belongs under `sasori_apps`.

The host factory keeps the existing `module:factory` contract and returns a
`Harness` bound to the caller-supplied `SQLiteStore`. A thin app-layer Harness
subclass may retain immutable loaded-plugin disclosure data, but it must not
override `run()`, `resume()`, `_continue()`, `_drive()`, approval, checkpoint,
recovery, or event behavior.

CLI and HTTP do not learn a plugin-specific execution path. They continue to
load one app factory and call the same Harness APIs. The HTTP owner loads a host
once during startup; requests and `/v1/apps` never rediscover or re-import a
plugin. The CLI creates the same host afresh for commands that require an app;
status and event projection remain app-free reads of durable state.

### 2. Alpha accepts only dependency-free external tools

An Alpha external plugin must be:

- a separately built and installed wheel, not part of the Sasori wheel;
- pure Python and `Root-Is-Purelib: true`;
- tagged `py3-none-any`;
- installed non-editably into the current interpreter's `purelib`;
- a single, non-namespace, exclusively owned top-level package;
- registered only in the exact `sasori.plugins` entry-point group;
- free of `Requires-Dist`, manifest dependencies, `.data` relocation, native
  extensions, `.pth`, console scripts, GUI scripts, and generated bytecode;
- `trusted_process`, with one or more tools and empty skills and workers.

The host rejects the entire configured generation if any enabled plugin falls
outside this scope. It does not silently ignore unsupported contributions.
Dynamic skills, workers, dependencies, multi-agent orchestration, lifecycle
hooks, middleware, and plugin-defined events remain deferred.

### 3. Runtime authority is one strict immutable lock

The operator explicitly selects one local lock file. It uses strict bounded
UTF-8 JSON, rejects duplicate keys, unknown fields, invalid Unicode and
non-finite numbers, and must equal Sasori's canonical encoding:

```text
ensure_ascii=false, sort_keys=true, separators=(",", ":"), allow_nan=false
```

The top-level identity is:

```json
{
  "schema_version": 1,
  "kind": "sasori.installed-plugin-lock",
  "catalog_sha256": "<lowercase SHA-256>",
  "plugins": []
}
```

Each plugin row binds these exact values:

- plugin ID and canonical manifest SHA-256;
- distribution name and exact version;
- entry-point group, name, and value;
- reviewed wheel filename, size, and SHA-256;
- dist-info directory and exclusive import root;
- installed `RECORD` size and SHA-256;
- every installed regular file's normalized path, exact size, and SHA-256;
- the exact `PermissionSet` grant, using the existing filesystem, network,
  host-process, secret, and `full_host` fields.

Plugin rows are sorted by plugin ID and file rows by path. Plugin IDs and paths
are unique. A grant must equal the reviewed manifest request exactly; Alpha does
not accept a stale superset merely because `PermissionSet.covers()` would allow
it. The existing permission disclosure remains truthful: effective access is
`FULL HOST PROCESS PRIVILEGES` and enforcement is false.

The lock binds the exact catalog bytes through `catalog_sha256`. It also repeats
the release's manifest and wheel identities so operators can audit the enabled
generation without joining separate files. Repetition must match the selected
catalog release exactly.

The runtime reads and verifies the lock once while constructing the host. It
does not watch or reload it. Missing, symlinked, non-canonical, truncated, or
mismatched locks fail closed.

### 4. A retained reviewed wheel is mandatory

The reviewed wheel remains available in the configured local wheel directory at
every host startup. Its basename, size, and SHA-256 must match both the lock and
the catalog release. Alpha does not treat an installed tree alone as evidence
of a reviewed artifact.

Wheel verification uses the standard library and reads every member. It
rejects encrypted entries, non-regular members, duplicate or case-fold-colliding
paths, traversal, unsafe Windows components, excessive counts or expansion,
multiple dist-info directories, unsupported wheel metadata, and malformed
metadata or entry points.

The wheel's `RECORD` must use only canonical `sha256=` URL-safe Base64 digests
without padding. Its path set must equal the wheel's regular-file inventory.
Every row except `RECORD` itself has an exact hash and decimal byte size that
match bytes read from the ZIP. `RECORD` has empty hash and size. Alpha does not
interpret `RECORD.jws` or `RECORD.p7s` as a verified signature.

Wheel `METADATA` name/version, `WHEEL` compatibility, and
`entry_points.txt` semantics must match the catalog manifest and lock before
installed files are considered.

### 5. Installed identity is a closed byte inventory

The lock is generated only after the reviewed wheel and the current installed
distribution have been checked together without importing plugin code. Wheel
members other than `RECORD` must appear at their supported purelib paths with
the same bytes. The installed `RECORD` may differ because the installer owns
it; its exact bytes and size are therefore stored in the Sasori lock.

The only installer-created files Alpha may accept are these dist-info files:

- `INSTALLER`;
- `REQUESTED`;
- a strict, non-editable `direct_url.json`.

They must appear in the installed `RECORD`, and their actual bytes are included
in the lock. No other unreviewed installed file is allowed.

At startup Sasori independently:

1. strictly parses the installed `RECORD` rather than trusting
   `Distribution.files`;
2. recursively scans the exclusive import root and dist-info directory;
3. requires the lock, installed `RECORD`, and actual scan to describe the same
   closed set of regular files;
4. re-hashes every file and checks its exact size;
5. checks that wheel-origin files still equal the reviewed wheel payload;
6. checks installed metadata and entry-point semantics again;
7. verifies that the entry-point module resolves inside the locked import root.

The host rejects editable markers, `.egg-link`, `.pth`, `__editable__` shims,
bytecode, namespace or shared packages, duplicate normalized distributions,
duplicate plugin IDs, pre-imported plugin modules, shadow imports, missing or
extra files, and every identity drift before any enabled entry point is loaded.

All enabled manifests are also checked for duplicate tool names before any
plugin import. Only after every configured plugin passes the catalog, artifact,
installed-byte, import-origin, permission, and tools-only preflight may the host
call the existing `load_enabled_plugins()` once. Registration validation after
import remains the final contract check.

### 6. Paths and file reads fail closed

Persisted paths are NFC-normalized relative purelib paths using `/`. A path is
invalid if it is empty, absolute, drive- or UNC-qualified, contains `\`, NUL,
ASCII controls, `:`, empty components, `.` or `..`, repeated separators,
Windows device names, trailing dots or spaces, or an NFC/case-fold collision.

Every locked leaf and intermediate component must remain a non-link ordinary
path. On Windows, junctions and other reparse points are rejected as well as
symbolic links. File hashing uses no-follow opens where available and checks
file identity and size before and after reading. A change observed during a
read fails verification.

This narrows ordinary check/use races but cannot make writable `site-packages`
immutable. A same-user or administrator process can still race the interval
between completed preflight and Python's later import open. Operators that need
resistance to a concurrent local attacker must use an immutable environment or
an isolation boundary. Alpha does not claim that property.

### 7. Generation changes require explicit stop, install, lock, restart

Sasori never invokes pip and never downloads, installs, upgrades, removes, or
rolls back a plugin.

The supported change sequence is:

1. stop Sasori processes that use the environment;
2. explicitly install the reviewed local wheel without bytecode generation;
3. generate and review a new lock from the selected catalog release, retained
   wheel, exact grant, and installed tree;
4. write canonical lock bytes to a same-directory temporary file, flush and
   fsync them, re-read and verify them, then replace the final lock atomically;
5. start a new Sasori process, which repeats the complete preflight.

The installer and lock replacement are not one filesystem transaction. A crash
between them leaves either the old complete lock or the new complete lock; if
that lock does not match the installed tree, startup rejects the plugin. There
is no automatic rollback. Rollback means explicitly reinstalling the previous
reviewed wheel, restoring or regenerating its lock, and restarting.

An already running process keeps its loaded objects. Updating files or the lock
does not hot-load, hot-unload, or change that generation. Drift is detected on
the next startup, not continuously.

### 8. Disclosure comes from the loaded object

The plugin-host application retains its frozen loaded-plugin records. Its
`/v1/apps` projection derives plugin ID, name, version, execution mode,
requested and granted permissions, effective access, enforcement status, and
tool ownership from those records. It must not infer an external plugin from a
fixed app ID or tool-name table.

The projection may add the lock's catalog, manifest, wheel, and installed-file
digests as audit fields, but it must not expose absolute installation paths or
environment values. Catalog projection never imports a plugin and never
re-runs its factory.

Bundled Incident, Research, and Developer disclosures remain explicitly static
until those applications elect to use the loader. This Alpha does not rewrite
their working direct-registration path.

## Manifest v1 boundary

The installed wheel hash protects the reviewed code bytes, but manifest v1's
semantic upgrade projection does not include every model-visible relationship:

- a tool digest omits `Tool.description`;
- a skill digest omits `SkillSpec.tool_names`.

Alpha does not silently change those digest meanings. Every external wheel
change requires a new reviewed catalog release, exact artifact hash, regenerated
lock, and restart even if the v1 upgrade diff does not expose the code-level
change. A later manifest schema v2 must bind tool descriptions and complete
skill tool relationships before dynamic skills or a general third-party market
can ship.

## Acceptance evidence

The Alpha is complete only when deterministic tests prove:

- a genuinely independent example wheel is built and installed outside the
  Sasori wheel;
- matching catalog, retained wheel, lock, installed bytes, exact grants, and
  import origin load the plugin once and expose its tools through one Harness;
- catalog/status and lock generation never import plugin code;
- tampering any catalog, wheel, wheel `RECORD`, installed `RECORD`, installed
  code/data/metadata, lock identity, grant, distribution, version, entry point,
  or import origin fails before every enabled plugin import;
- unsupported dependencies, editable installs, links/reparse points, bytecode,
  shared packages, skills, and workers fail closed;
- two enabled manifests with the same tool name fail before import;
- the external tool uses the same Python, CLI, and HTTP Harness path;
- an external side-effecting tool pauses for approval, resumes explicitly, and
  commits one effect across restart without bypassing existing recovery rules;
- `/v1/apps` projects the real loaded permission and tool ownership data and
  does not trigger another load;
- atomic lock replacement preserves the prior final file on failure;
- Windows and Linux tests cover their relevant path/link behavior.

## Deferred

- automatic pip invocation, dependency resolution, and environment creation;
- publisher identity, artifact signing, attestations, TUF, Sigstore, and remote
  revocation;
- a hosted or federated marketplace and an install button;
- sandboxing, enforced capabilities, per-plugin process or container isolation;
- editable, namespace, shared-package, native, platform, or dependency-bearing
  wheels;
- runtime file monitoring, hot load/unload, and generation switching;
- dynamic skills, workers, digital employees, and multi-agent orchestration;
- manifest schema v2 and a complete model-visible contract digest;
- automatic installation rollback or exactly-once package management.

## Consequences

This decision makes the first third-party path useful but intentionally strict.
An operator can review, install, lock, load, run, and disclose a real external
tool plugin without adding another Agent loop or pretending trusted Python is
isolated. The cost is a narrow wheel format, an explicit restart workflow, a
retained local artifact, and hashing the installed tree at startup. Broader
marketplace convenience must not weaken this identity boundary.
